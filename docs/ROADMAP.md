# RepoLens 路线图

四个里程碑，每个里程碑结束时都是一个**可用**的工具，而不是半成品。

目标语言：TypeScript / JavaScript、Python、Go、Rust
目标规模：1400 文件 / 40 万行量级的 monorepo（参照 [earendil-works/pi](https://github.com/earendil-works/pi)）

---

## M1 · 结构骨架（确定性，零 LLM 依赖）

**目标**：`repolens open .` 能扫描任意仓库，在浏览器里看到包级架构图和目录结构，
并能点进任意文件看到它定义了哪些符号。全程不需要任何 API key。

### 交付内容

- [x] pnpm monorepo 骨架，四个包，TypeScript 项目引用构建链
- [x] 领域类型与 SQLite schema
- [x] 文件发现：`.gitignore` 遵循、默认忽略、role 分类（source/test/config/generated/types/docs）
- [x] 语言检测、monorepo 包检测（pnpm/npm workspace、go.mod、Cargo workspace、pyproject）
- [x] tree-sitter 解析池（`@vscode/tree-sitter-wasm`）
- [x] 四语言符号抽取：函数、方法、类、结构体、接口、类型别名、枚举、常量
- [x] 四语言 import 抽取 + 文件级模块解析
- [x] 内容指纹与增量扫描
- [x] 指标：LOC、圈复杂度、导出数
- [x] 文件级依赖边聚合到目录级、包级
- [x] CLI：`scan` / `serve` / `open` / `info`
- [x] HTTP API：overview / tree / packages 图 / 子图展开 / 文件详情 / 符号详情 / 搜索
- [x] Web：包级架构图（React Flow + ELK in Worker）、目录树热力、详情抽屉、hover 卡片

### 验收标准

- [x] 扫描 RepoLens 自身，全量 < 5s → **0.35s**
- [x] 扫描 `earendil-works/pi`（1400 文件），全量 < 60s，增量 < 3s → **9.3s**
- [x] 首屏节点数 ≤ 30，渲染 < 500ms
- [x] import 解析率：TS ≥ 95%，其他语言 ≥ 85%（未解析的需可查）

  四种语言各在真实仓库上实测：

  | 仓库 | 语言 | 规模 | 解析率 |
  | --- | --- | --- | --- |
  | RepoLens 自身 | TS | 13.7k 行 | 100% |
  | earendil-works/pi | TS | 342k 行 | 99.9% |
  | gomux | Go | 6.5k 行 | 100% |
  | pyreq | Python | 15.7k 行 | 99.7% |
  | BurntSushi/ripgrep | Rust | 49k 行 | 99.5% |

  Rust 一开始只有 84.8%，根因是解析器硬认 `<包目录>/src` 作为 crate 根。
  Cargo 允许 `[lib]` / `[[bin]]` 用 `path` 把入口指到任意位置，ripgrep 的根包
  就声明了 `[[bin]] path = "crates/core/main.rs"`，于是 `crate::flags::lowargs`
  实际落在 `crates/core/flags/lowargs.rs`。改成从清单里显式声明的入口反推
  crate 根、再补上 Cargo 自动发现 target 的四个约定目录（`tests` / `benches` /
  `examples` / `src/bin`，目录内每个 `.rs` 各自是一个 crate 根）后到 99.5%。
  连带效果是 Rust 的确定调用边从 1,546 涨到 2,109——import 解析得准，
  调用链接器才有东西可用。

  剩余未解析都是有据可查的两类：说明符最后一段是符号名而非模块名
  （`ModuleResolver` 契约只给 specifier，拿不到 specifier 列表，需留到 link 阶段），
  以及 `super` 层数超出当前模块深度。

## M2 · 符号级调用图与交互打磨

**目标**：能追一个函数的调用链，看到它的签名和传参，并且图在 1400 文件规模下依然可操作。

### 交付内容

- [x] 符号索引：导出名 → 符号 id
- [x] 调用点链接：AST 调用点 → 目标符号，四档置信度（`exact` / `likely` / `ambiguous` / `external`）
- [x] 方法调用启发式：`this.` / `self.` 命中所属类、命名空间 import、可见类型作用域约束
- [x] 类型关系边：`extends` / `implements` / 结构体嵌入 / trait 实现
- [x] 函数签名解析：参数名、类型、默认值、可选性、返回类型
- [x] 渐进式下钻：包 → 目录 → 文件 → 函数，四级
- [x] 文件内符号图带调用边
- [x] 以符号为中心的 N 跳调用图（方向 / 跳数 / 置信度可调，横向布局）
- [x] 截断如实上报：中心节点省略了多少条边会显示在顶栏
- [x] 多义调用在详情里摊开全部候选
- [x] 完整手势体系落地（见 [INTERACTION.md](./INTERACTION.md) 手势语义表）
- [x] 折叠节点的层叠卡片渲染与 fan-out 预览
- [x] ⌘K 命令面板（按 role 过滤，与图谱的噪音开关一致）
- [x] 详情抽屉的传参表、源码标签页、关系标签页
- [ ] `export *` 传递闭包（当前退化为全局唯一名匹配，落在 `likely`）
- [ ] 两点间依赖路径查找（SQL 递归 CTE）
- [ ] 过滤抽屉（噪音/外部依赖两个开关目前直接放在顶栏，够用就先不加）

### 验收标准

- 调用边 `exact` 占比：TS ≥ 80%
  → **实测 59.9%**（pi：exact 28,386 / 已链接到符号的 47,422）。
  缺口全在无接收者类型信息的方法调用上：它们靠「宿主类在本文件可见」
  这条作用域约束落在 `likely`。要再往上走需要真正的类型推导，
  代价远大于收益，暂不追。
- [x] 从任意入口函数可追 5 层调用链，每层展开 < 300ms
- [x] 手势响应满足 [性能预算](./INTERACTION.md#性能预算)

## M2.5 · 架构体检（确定性，零 LLM 依赖）

**目标**：工具从「忠实渲染」变成「能指出哪里不对」。

这个里程碑原本不在计划里，是从项目出发点倒推出来的：人需要的不只是看清
AI 写出来的架构，更是**判断它合不合理**。而判断的第一步可以完全确定性地做，
不必等 LLM。

### 设计原则：宁可漏报不可误报

这一层的全部价值在于节省注意力，所以每条判据都写成「排除掉所有能想到的
正常情况之后还剩下的」。实测教训：

- 朴素的循环依赖检测在 pi 上报 43 对，其中 **38 对（88%）是祖先/后代包含关系**
  （`core/src ⇄ core/src/db` 只是 `index.ts` 引用 `db/`、`db/*` 又引用 `../types.ts`），
  排除后只剩 5 对真兄弟循环
- 孤儿导出朴素检测报 1401 个，但库的公开 API 本来就没有内部调用者；
  筛到「所在文件根本没人 import」只剩 110 个，里面还混着 `examples/` 这类
  独立入口——精度不够，暂不交付

一个会乱叫的诊断比没有诊断更糟：它消耗的正是它本该节省的东西，而且只要
错过一次，人就再也不会认真看第二次。

### 交付内容

- [x] 结构指纹：忽略标识符与字面量后的 AST 形状哈希，在 `parseFile` 统一计算
- [x] 重复实现检测：跨文件形状相同的函数/方法；同名判 high，异名判 low
- [x] 循环依赖检测：包级与目录级，排除祖先/后代包含关系
- [x] findings 表 + 按路径前缀上卷，任意层级都能看到「这底下有问题」
- [x] 图节点体检角标（含子孙汇总），问题出现在人已经在看的地方
- [x] 左侧面板「体检」标签页，与结构树共用槽位，不新增门面
- [x] 顶栏体检入口，仅在真有问题时出现
- [x] `/reveal/:nodeId` 祖先链接口：从清单或搜索一键把图带到目标所在层
- [x] `keep` 参数：被跳转的目标不允许折进聚合节点
- [x] 视口内容边界钳制，展开时不再把兄弟节点顶到可视区外
- [ ] 孤儿导出（精度不足，需要先细化 `examples/` 等 role 分类）
- [ ] 层级倒置（需要先有分层识别，依赖 M3）
- [ ] 巨石文件/函数离群检测

### 验收标准

- [x] 误报为零：RepoLens 自身 2 组重复 + 2 组循环，逐条人工核对全部成立
- [x] 大仓可用：pi（34 万行）109 组重复 + 6 组循环，扫描耗时 9.4s 未退化
- [x] 不静默失效：四种语言的指纹覆盖率均为 100%，Go/Python 报 0 组是真干净
      （候选池里确有形状相同的组，被「跨文件才算重复」正确排除）

**自体检发现的真问题**：四个语言抽取器各自重写了 `countArgs`、`annotationText`——
逐字节相同。pi 里 `toError()` 在 3 个包 6 处各写一遍，而 `client/src/errors.ts`
本来就导出了它。这正是 AI 参与写码的特征病征：按语言、按场景各生成一遍，
而不是抽出共用。

## M3 · LLM 语义层

**状态：已完成。**

**目标**：图上的每个节点都有一句人话解释，函数点开能看到逻辑伪代码。

### 交付内容

- 可插拔 LLM 客户端：OpenAI 兼容接口，配置文件切换 base URL / model / key
- 支持本地 Ollama 与自定义网关；无 key 时优雅降级（纯结构模式）
- 扫描期生成：仓库总览、包/目录摘要、架构分层识别与命名
- 按需生成：函数摘要、逻辑伪代码，结果写入 SQLite 缓存
- 缓存失效：绑定符号内容指纹，代码变了才重新生成
- 并发控制、重试、token 预算上报
- 生成语言默认中文，可配置
- UI 明确标注 AI 生成内容，与确定性内容视觉区分

### 验收标准

- 全量扫描的 LLM 调用只覆盖包/目录级（数量级 < 100 次），不做全量函数预生成
- 单个函数伪代码生成 < 5s
- 无 API key 时 M1/M2 功能完全不受影响

## M4 · 关键链路与数据流

**状态：已完成。**

**目标**：回答「一个 HTTP 请求进来，代码是怎么走到数据库的」。

### 交付内容

- [x] 入口识别：`main` 函数、CLI 命令注册、HTTP 路由注册、导出的公共 API、测试入口
- [x] 边界识别：数据库访问、网络请求、文件系统、消息队列、外部进程
- [x] 链路追踪：从入口沿调用边走到边界，产出有序步骤
- [x] 链路视图：泳道式 / 时序式渲染，区别于依赖图的分层渲染
- [x] 链路的 LLM 叙述：每一步在做什么，关键传参怎么流动
- [x] 数据结构流转：某个类型在链路上经过哪些函数

### 验收标准

- [x] Express fixture 自动识别 `GET /users/:id`，沿确定调用边追到 `db.query`
- [x] FastAPI 装饰器路由由 AST 识别；Express/Fastify/Gin/Axum 注册语法均有规则覆盖
- [x] 链路步骤中确定性步骤与推断步骤在 DTO 和 UI 中可区分

### 实现边界

入口、边界与有序路径完全由 AST、符号表和调用边生成；LLM 只在用户点击后解释
既有步骤。路径只遍历 `exact` / `likely`，遇到环会停止，默认最多 8 层、每入口
24 条到边界的最短路径。类型流来自函数参数和返回类型，因此统一标为“签名推断”，
不声称是运行时值追踪。

入口列表默认只展开可到达 I/O 边界的入口；未形成链路的候选折叠展示，测试入口跟随
“显示杂项”开关。公共 API 只从包入口文件及其 re-export 链识别，CLI 注册要求明确的
框架接收者证据，避免把任意 `command()` / `action()` 调用当作命令行入口。
